# Architecture rules

- Tracking validation is shared from `supabase/functions/_shared/trackingValidation.ts`; recognition comes only from official 17TRACK evidence and is server-owned. The existing lifecycle job performs per-parcel checks at 24 h, 48 h and daily thereafter, and a persistent tracking-review marker prevents automatic payout retries from bypassing manual review.

- Guard authenticated pages with `ProtectedRoute` and resume only validated same-origin destinations through the public `/auth/callback`; include the destination in callback URLs so email confirmation survives a different browser, without bypassing reservation RLS.
- Transaction lifecycle emails carry `reservationId` and notifications store `/transaction/:id` in their existing link field; keep unpaid exclusivity and admin dispute links separate because the transaction page is participant-only.

- Use `needsStripeOnboarding` for payment setup card visibility and `shouldShowStripeActionBadge` for its action badge, so both follow the same onboarding rule while the badge stays limited to accounts that already sent a proposal.

- Role-conviction pages share `RoleLandingPage`; keep their structure synchronized while content remains locale-driven.- The `app_settings.beta_open` switch disables the account-to-waitlist invitation flow; any future signup restriction must also respect it, and normal sign-in/sign-up must never depend on that flow.
- Fee rates and calculations live only in `src/lib/fees.ts` and its mirror `supabase/functions/_shared/fees.ts` (kept identical, both covered by `src/lib/fees.test.ts`), so client display and Stripe checkout never diverge.
- Each paid purchase/sale has a dedicated page at `/transaction/:reservationId` (`src/pages/Transaction.tsx`); access is enforced by the existing `reservations` RLS (buyr/findr only — no row means the NotFound page), and its progress steps derive from `payment_status`, `delivery_type`, `shipped_at` and `delivered_at`, never from a single raw field alone.
- The findr ship-from address lives in private `profiles.ship_from_*` columns (never in column-level SELECT grants), read via `get_my_profile()` and written only via `update_ship_from()`; it is snapshotted to `reservations.ship_from` by stripe-webhook at payment, server-only, and purged daily by `purge_reservation_ship_from()`.
- Shipping estimates derive only from admin-maintained `shipping_rates` via `src/lib/shippingEstimate.ts` (cheapest covering bracket per carrier+mode, then min/max), and render nothing when no rate applies, so no price is ever invented.
- Reservation payment statuses shared by server functions live in `supabase/functions/_shared/paymentStatus.ts`; the label flow is gated by `app_settings.label_flow_enabled`, read on every server run via `loadLabelFlowEnabled` (initial status, 3-day deadline, label emails) and on the client via `useFeatureFlags().labelFlowEnabled` (also gates the shipping estimate); off means new payments start in `paye_en_attente_reception`, on means `paye_attente_etiquette`, while already-paid reservations keep their status, and label fields are server-only via `guard_tracking_evidence`, with label files in the private `labels` bucket under `<reservation_id>/`.
- Buyr label upload rules (file signature/size/active-PDF checks, eligibility, `etiquette_refusee` status) live in `supabase/functions/_shared/labelFlow.ts`, covered by `src/lib/labelFlow.test.ts`; `provide-label` refuses everything while `label_flow_enabled` is off and moves the reservation to `paye_en_attente_reception` with a conditional update.
- Label downloads go through `label-download`: POST (buyr/findr JWT) returns a 60 s HMAC-signed URL to the same function, whose GET serves the private file with `Content-Disposition: attachment` and `nosniff`; `canAttachLabel` in `labelFlow.ts` decides email attachment (no PDFs with `/ObjStm`).
- Label files are purged daily by `purge-labels` (cron_secret-protected) using `isLabelPurgeable` in `labelFlow.ts`; label-download signs links with the dedicated `label_download_secret` row in `webhook_secrets`, never the service key.
- Findr label actions (`reject-label`, `declare-dropoff`) share `checkFindrLabelEligibility`/`planLabelRejection` in `_shared/labelFlow.ts`; `dropoff_declared_at` is a server-only declaration with no payout effect, and full refunds go through `_shared/refundReservation.ts` so cancellation and label rejection refund identically.
- `tracking_recognized` means a first physical carrier scan (`PHYSICAL_SCAN_STATUSES` in `_shared/trackingEvidence.ts`, InfoReceived excluded); label-flow shipment is detected only via `_shared/shipmentDetection.ts` (pure rules in `shipmentRules.ts`) (webhook and hourly job), and receipt confirmation is allowed only from `expedie`/`livre` via `receiptConfirmationError`.
