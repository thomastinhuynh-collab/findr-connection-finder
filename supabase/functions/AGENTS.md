# Server function rules

- Buyr label upload rules (file signature/size/active-PDF checks, eligibility, `etiquette_refusee` status) live in `supabase/functions/_shared/labelFlow.ts`, covered by `src/lib/labelFlow.test.ts`; `provide-label` refuses everything while `label_flow_enabled` is off and moves the reservation to `paye_en_attente_reception` with a conditional update.
- Label downloads go through `label-download`: POST (buyr/findr JWT) returns a 60 s HMAC-signed URL to the same function, whose GET serves the private file with `Content-Disposition: attachment` and `nosniff`; `canAttachLabel` in `labelFlow.ts` decides email attachment (no PDFs with `/ObjStm`).
- Label files are purged daily by `purge-labels` (cron_secret-protected) using `isLabelPurgeable` in `labelFlow.ts`; label-download signs links with the dedicated `label_download_secret` row in `webhook_secrets`, never the service key.
- The findr label action `reject-label` uses `checkFindrLabelEligibility`/`planLabelRejection` in `_shared/labelFlow.ts`; there is no findr drop-off declaration (`dropoff_declared_at` is kept but unused) because shipment is proven only by the carrier scan, and full refunds go through `_shared/refundReservation.ts` so cancellation, label rejection and deadline expiries refund identically.
- First-scan deadline rules for provided labels (7 days after `label_provided_at`, findr reminders at 2/5 days with a team alert at 5, buyr self-cancel from 5 days) live in `supabase/functions/_shared/scanDeadline.ts` (re-exported by `src/lib/scanDeadline.ts`, covered by `src/lib/scanDeadline.test.ts`) and are applied by the hourly job after its shipment-detection step.
- Label deadline rules (24 h/48 h reminders, expiry cancellation, buyr self-cancel before label) live in `supabase/functions/_shared/labelDeadline.ts`, covered by `src/lib/labelDeadline.test.ts`; the hourly job notifies only after a successful refund, and `refundAndCancelReservation` uses an idempotency key per reservation so retries never refund twice.
- Post-payment messages (findr proposal_accepted, buyr payment_confirmed, findr ship_from_needed) take their text from `supabase/functions/_shared/saleMessages.ts` (covered by `src/lib/transactionEmails.test.ts`), choose the variant from `payment_status` (`paye_attente_etiquette` = label flow), and are sent only by the stripe-webhook run whose conditional payment update succeeds, so duplicate Stripe events never resend them.
